Run boundaries in concatenated recordings

Runs from one session are concatenated before extraction so that every run gets the same ROIs. Does the jump between runs hurt the z-correction, and does the choice of z-position estimator matter there? 5 concatenated recordings were checked, chosen for what changes between runs: nothing, laser setting, an unexplained drop in brightness, and a 9 µm stage refocus.

Written for the Wang lab 2P group. Pipeline: Suite2p extraction, non-rigid F_anat (60 px patches), per-ROI fit in ΔF/F. Data: Scnn1aAi14_D1M2 08/29 and 08/21/2026, Scnn1aAi14_B2M0 04/22/2024, C57_O1M2 10/19/2023, Scnn1aAi14_2P11 07/11/2024; 16×, 765 × 765 px, 20 Hz. Code: validation/boundary_benchmark.py.

Summary

Fit each run with its own baselineWith one ΔF/F baseline over the concatenated trace, a fluorescence step between runs drives the per-ROI slope. Per-run baselines leave 3–12× less z-dependence inside the runs, in every recording and with both depth rules. This is now the pipeline default.
Most steps between runs are not depthFluorescence changed by 18–25% at three boundaries where depth predicts 1–6% (laser setting +4% and +8%; a 21% drop in raw brightness of unknown cause). Only the 9 µm refocus produced a step that depth explains (r = 0.81).
The Suite2p-style failure was a bugOur port handed the movie to parallel workers as a strided memmap view; for C-order CaImAn memmaps the workers read wrong pixels and the estimate piled up at the first and last planes. Fixed. Since then it tracks the Pearson estimate, including across every boundary.
Keep the Pearson estimatorWith soft depth, which the auto mode selects, the estimators give the same correction (differences ≤ 0.1 points of %). With argmax depth the differences are small and change sign between recordings. Pearson is also 1.4–1.7× faster.

Leaving out the first 200 frames (10 s) of each run from the fit does not help, so boundary_exclude_frames stays at 0. When the step is real depth (2P11), per-run baselines are still better: a 10-plane step sits outside the range where F follows depth linearly, and with one baseline it dominates the slope.

Pipeline change: run_roi_zcorr reads the frames of each run from stim_sequence.json (now also written per run) and computes ΔF/F baselines per run; the slope is shared by all runs. Option roi_correction.per_run (default true). The auto depth mode skips z-events whose window spans a boundary. The MATLAB analysis computes ΔF/F with per-trial baselines, which already removes steps between runs.

3 · z-position estimators

The pipeline estimates z-position by Pearson correlation of each smoothed frame with the shifted z-stack, then applies a 5-frame median filter. The Suite2p-style estimator (compute_zcorrel_suite2p, Suite2p's masked phase correlation) had been set aside because it "latched onto the deepest plane" on motion-corrected movies.

The cause was in our port, not in Suite2p: it passed the whole movie to joblib workers, and a C-order memmap reshaped to frames is a strided view that the workers read with the wrong pixel order. Each task now receives one contiguous frame. Results on F-order memmaps (all current pipeline exports) are unchanged, verified identical on B2M0. The pipeline's own Pearson path was never affected.

With argmax depth, the Suite2p-style estimate explains 0.1–0.5 points of % more on three recordings, less on one (B2M0) and the same on one; dropping the median filter from the Pearson estimate helps on two (p < 0.01), slightly on a third (2P11, p = 0.02) and makes no difference on two. With soft depth none of the differences exceeds 0.1 points of %. Soft depth searches ±8 planes around the global z-position for each patch, so the global estimate only has to be close. No estimator fails at a run boundary.

Open items

  • Detection: whether the step at a boundary creates or merges ROIs in Suite2p was not tested.
  • Suite2p deconvolution runs on the concatenated trace. On D1M2 08/29 the event rate in the 5 s after the boundary was 1.22× the run median (1.12× after the start of run 1); not studied further.
  • On the cluster, ~/.cache points to scratch, which the 2p_proc container does not mount, so CaImAn's import of pynwb fails. Passing APPTAINERENV_XDG_CACHE_HOME=/tmp/xdg_cache works around it; the template script could set it.
